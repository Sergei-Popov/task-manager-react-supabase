# Правила для ИИ-агентов

Этот файл — пошаговая инструкция для любой модели, которая работает с репозиторием.
Следовать буквально. Если правило и удобство конфликтуют, побеждает правило.

## 0. Перед началом любой задачи

1. Прочитать `CLAUDE.md`, `CONTEXT.md` и релевантные разделы `docs/`.
2. Использовать термины из `CONTEXT.md`. Если пользователь употребил другой термин,
   уточнить, что имеется в виду.
3. Проверить `docs/adr/`: не нарушает ли задуманное принятые решения.

## 1. Понять задачу до кода (гриллинг)

Никогда не начинать реализацию фичи или исправление бага по одному описанию.
Сначала интервью через навык `grilling` (`/grill-me` или `/feature`, `/bugfix`):

- вопросы задаются раундами, каждый с рекомендуемым ответом;
- факты (как устроен код, что в базе) агент выясняет сам, у пользователя спрашивает
  только решения;
- интервью закончено, когда не осталось невысказанных допущений, и пользователь
  подтвердил понимание.

Результат фиксируется в `docs/specs/<дата>-<slug>.md` (для фич) или в описании бага
с шагами воспроизведения (для багов). Реализация начинается только после
подтверждения пользователя.

## 2. Реализация

- Логика запросов только в `src/utils/api.js`; состояние дашборда только в
  `DashboardPage.jsx`; SQL только в `server/src/routes/*` с фильтром по `req.user.id`.
- Новый компонент интерфейса — из shadcn/ui (`npx shadcn@latest add`), не самописный.
- Строгий стиль (ADR-0004): токены темы, без цветных полосок и градиентов.
- Тексты, комментарии, сообщения ошибок на русском.
- Изменение схемы БД — только новой миграцией `server/migrations/000N_*.sql`.
- Изменил API — обновил `docs/API.md`. Изменил архитектуру — `docs/ARCHITECTURE.md`.
  Новый термин — `CONTEXT.md`. Важное необратимое решение — ADR.

## 3. Проверка (обязательно, без исключений)

После каждого изменения выполнить `docs/TESTING.md`:

1. `npm run lint` и `npm run build`.
2. Функциональная проверка затронутого сценария через браузер и/или curl, сверка с
   базой данных.
3. Визуальная проверка скриншотами на 1280 и 390 px, скриншоты открыть и посмотреть.
4. Консоль браузера без ошибок.
5. Найденные ошибки исправить и проверить заново. Отчёт содержит список того, что
   проверено и как.

Команда `/verify` делает это по протоколу.

## 4. Завершение

- Убрать временные файлы (`.playwright-mcp/`, скриншоты, отладочные логи с
  префиксом `[DEBUG-…]`).
- Коммит с понятным сообщением на английском, в теле перечислить, что сделано.
  Пуш только по просьбе пользователя.
- Для выкладки production-сборки: `/ship`.

## 5. Чего не делать

- Не возвращать Supabase и любые BaaS.
- Не трогать серверы других проектов (ssh-mcp из admin-platform-bots).
- Не использовать `window.confirm`/`alert`, CSS-модули, эмодзи как иконки интерфейса.
- Не писать `fetch` в компонентах, не обходить `validateBody`.
- Не отчитываться о выполнении без реальной проверки в браузере.

## 6. Если что-то непонятно

Спросить. Один точный вопрос лучше, чем реализация не того. Формат вопросов —
как в навыке `grilling`: номер, суть, рекомендуемый ответ.
