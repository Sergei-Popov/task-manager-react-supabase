# /bugfix — от описания бага до проверенного исправления

Аргумент — описание бага словами пользователя. Шаги строго по порядку.

## Шаг 1. Понять баг (короткий гриллинг)

Вызвать навык `grilling`. Цель — получить ответы на:

1. Точные шаги воспроизведения (с какого экрана, какие данные, какая ширина/устройство).
2. Что ожидалось и что произошло (текст ошибки, скриншот, если есть).
3. Всегда или иногда; когда началось (после какого изменения).
4. Что считать исправленным: критерий приёмки одной фразой.

Всё, что можно узнать самому (логи API, состояние базы, консоль браузера,
`git log` затронутых файлов), выяснить без вопросов пользователю. Записать итог в
ответ пользователю блоком «Воспроизведение / Ожидается / Фактически / Критерий».
Дождаться подтверждения «да, это оно».

## Шаг 2. Воспроизвести

Вызвать навык `diagnosing-bugs` и выполнить его фазы 1–2: построить быстрый
повторяемый сигнал (curl к API на :3001, psql, сценарий Playwright по
`docs/TESTING.md`), увидеть, как он «краснеет» именно на описанном симптоме.
Если воспроизвести не удалось — честно сказать, что пробовали, и запросить у
пользователя данные (скриншот, шаги, аккаунт).

## Шаг 3. Найти причину и исправить

Фазы 3–5 `diagnosing-bugs`: 3–5 гипотез с проверяемыми предсказаниями, точечная
инструментация с префиксом `[DEBUG-xxxx]`, исправление минимального объёма.
Правила кода из `docs/AI-RULES.md` раздел 2 действуют и здесь.

## Шаг 4. Проверить

Прогнать сигнал из шага 2 — должен стать «зелёным». Затем вызвать навык `verify`
с указанием затронутых экранов. Убрать всю отладочную инструментацию
(`grep -rn "DEBUG-" src server`). Ошибки при проверке исправить и повторить.

## Шаг 5. Зафиксировать

Если баг связан с непониманием термина или решения, обновить `CONTEXT.md` или
`docs/`. Коммит с сообщением, где в теле названа реальная причина бага. Пуш только
по просьбе. Отчёт: причина, что изменено, чем проверено.
